# 課題担当 A（rb1-01〜rb1-11）が置いた仮定

作成日: 2026-09-12。根幹文書（`docs/01-core-spec.md`）・設計文書（`docs/10-design-ruby-basic.md`）・
基盤の手引き（`ruby-core-materials/docs/`）のいずれにも規定が無いため、実装者が決めた事柄を列挙する。
後で根幹・設計へ書き写すかを判定するための一覧であり、それ自体は規定ではない。

## 1. 手本の原本に対する編集

1. **同名メソッド・同名クラスが 1 ファイル内で衝突するときは改名した。** 根幹 §7 の
   「課題化の編集として認めるもの」は改名を「minitest と衝突する識別子」に限っている。
   しかし公式ドキュメントは同じ名前（`add_values` / `class A` / `hi`）を段階的に上書きしながら
   説明するため、1 ファイルにまとめると後の定義が前を壊す。**衝突を避けるための改名も
   認められる編集として扱い、改名したことと原名を `commentary.md` の「原典との差分」に明記した。**
   該当: rb1-08（`add_values` 系 8 個）、rb1-10（`A` → `Owner` / `Reopened` / `Attrs`）。
2. **原典が段階的に組み立てるコードは、最終形だけを手本に置き、途中形は `commentary.md` に引用した。**
   該当: rb1-02 の `def hi`（3 段階のうち最終形のみ）。
3. **行数の上限（根幹 §3.1 の 80 行）に収まらない節は手本から外し、`commentary.md` に
   コードごと引用した。** 該当: rb1-10 の `protected` の例、rb1-02 の
   `if __FILE__ == $0` ブロック（課題 19 の範囲でもあるため）。
4. **`# frozen_string_literal: true` を全ファイルに置いた結果、原典の例がそのままでは
   再現しない箇所に `.dup` / `+""` を足した。** 凍ったリテラルは同一オブジェクトに共有され、
   書き換えもできないため。該当: rb1-06（`"george".dup.object_id`、`force_encoding` の受け手）。
   これは「空白と引用符の整形」の枠を超える編集なので `commentary.md` に明記した。
5. **警告を消すための括弧の追加を行った。** `refute_match /^no/i, x` は Ruby が
   「あいまいな第 1 引数」の警告を出すため `refute_match(/^no/i, x)` にした（rb1-03）。
   根幹 §3.1 は「メソッド呼び出しの括弧は検査しない」としか書いておらず、括弧の追加が
   認められる編集かは規定が無い。意味を変えない整形として扱った。

## 2. 課題文書（README）の書式

6. **書き写し課題（rb1-02〜rb1-11）の README は 1 つの雛形から生成し、節の構成と手順の要素を
   完全に同一にした。** 根幹 §4.2「同形式間の整合」を機械的に満たすため。
   課題ごとに変わるのは、到達点・手本のファイル名と実行サマリ・確認課題の中身だけ。
7. **rb1-05 にだけ手順を 1 つ足した**（「スクリプトとして端末から 1 度動かす」）。
   設計 §3.2 がこの課題で「`ruby` コマンドでのスクリプト実行・標準入力のリダイレクト・
   `echo $?`」を初出の道具としているのに、書き写しの手順だけでは端末から使う機会が無いため。
   README 本文にこの差の理由を書いた（根幹 §4.2「同形式間の整合」が要求する説明）。
8. **教材リポ・成果リポ・課題番号の呼び名を rb1-01 の README で定義し、rb1-02 で 1 度要約した。**
   根幹 §4.2「語彙の自己完結」のため。以降の課題では既知として使っている。
9. **「確認課題」という語を、統治側の形式名ではなく学習者向けの普通名詞として使った**
   （「手本を一箇所変える／実装する小さな課題」の意味）。各 README の手順の中で意味が分かるように書いた。
10. **`.gitignore` の中身を `/vendor/` と `/.bundle/` の 2 行にした。** 設計 §5 は
    「`.check/` は含めない」としか書いていない。`bundle config set --local path vendor/bundle` を
    課題 1 の手順に入れた結果として必要になった 2 行である。
11. **課題 1 の `progress.md` 雛形に「状態の言葉」の節を入れ、4 つの状態語を定義した。**
    根幹 §8 が「統治文書を読まないと運用できない台帳を作らない」と求めているため。
    週あたりのセッション数の決め方（最初の 2 週間の実績の平均で書き直す）も雛形に書いた。
12. **成果リポのコミットを各課題の最後の手順に入れた。** 根幹 §4.7 は基礎の成果リポも公開すると
    決めているが、いつコミットするかは規定が無い。課題ごとに 1 コミットとし、
    メッセージの例を README に書いた。

## 3. 確認課題の設計

13. **デバッグ型（rb1-04・rb1-05）の欠陥は、雛形ファイルそのものに仕込んだ。**
    設計 §3.1 は「所在と修正方針を課題文書に書かない」とだけ定めている。
    雛形の冒頭コメントには「このコードには欠陥がある」とだけ書き、場所は書いていない。
14. **デバッグ型の README に「判定テストを書き換えない」「いま通っているテストを落とさない」の
    2 条件を明記した。** 仕様の同一性を保つため。設計に規定は無い。
15. **rb1-09 の「Proc / lambda の選択に中立」を、テストが引数の数の厳しさにも `return` の挙動にも
    依存しないことで担保した。** 実機で 2 つの参照解答（ブロックを Proc のまま持つ版と
    `->(value) { step.call(value) }` で包む版）を作り、どちらも同じ judge 結果になることを確認した。
16. **出力予測（rb1-07 の 2 本、rb1-09 の 1 本）の題数は実装者が決めた。** 設計 §3 は
    課題 7・9 に出力予測型を置くとだけ書き、本数を決めていない。rb1-07 は Array 系と Hash 系で
    1 本ずつ、rb1-09 は `return` / `break` / `next` / lambda の対比を 1 本にまとめた。
17. **出力予測の対象コードは、実行するたびに同じ出力になるものだけにした**（乱数・時刻・
    オブジェクト ID・ハッシュの列挙順に依存するものを避けた）。判定が完全一致であるため。
18. **確認課題テストのクラス名を `Rb1NN<名前>ExerciseTest` の形にした。** 手引き §1 が
    「課題ごとに一意」とだけ求めているので、失敗表示から課題番号が読める形にした。

## 4. judge の構成

19. **確認課題が出力予測型のときは、`exercise_test` を並べずに `predict` を並べた**（rb1-07）。
    設計 §5 の judge 表は形式ごとに judge を決めているが、「書き写し課題の確認課題が
    出力予測型のとき」の組み合わせを書いていない。
20. **確認課題が 2 つある rb1-09 では `exercise_test` と `predict` を両方並べた。**
21. **`assertion_count` の `min` は、原本を実機で走らせた実行サマリの値をそのまま書いた**
    （手引き §2 のとおり）。実測値は教材リポの外の作業場（`~/lab/ruby-learning/.worktmp/` 配下の実装記録）に残した。

## 5. 記録ファイル

22. **課題ごとの実装記録を教材リポの外の作業場（`~/lab/ruby-learning/.worktmp/` 配下）に置き、節構成を
    実行環境 / 計測値 / 参照解答での `bin/check` 実行の 3 つにした。**
    指示は「全 judge 合格の実行ログを残す」とだけ定めている。
    rb1-02 の分にだけ、書き写し形式の代表として判定機構の検出力の確認結果を足した。
23. **参照解答を置いた模擬成果リポは `~/lab/ruby-learning/.worktmp/ruby-core-A`。**
    `Gemfile` / `Gemfile.lock` / `.bundle/config` / `vendor/bundle` は基盤担当が作った
    `ruby-core-sample` から複写した（設計 §5 の成果リポ初期ファイルと同じ内容）。

## 6. 基盤・設計に返す申し送り

24. **設計 §2 の B13 が挙げる csv / logger の版は、`bin/check` の判定には関わらない。**
    rb1-01 の `Gemfile` には設計 §5 のとおり `minitest` / `debug` / `irb` の 3 つだけを書いた。
25. **鍵ファイルの要否を実測で確かめた。** rb1-01〜rb1-11 はすべて非封緘なので、
    `RUBY_LEARNING_SEAL_KEY_FILE` を外し、既定の `~/.config/ruby-learning/seal.key` も無い状態で
    `bin/check` も `bin/check --start` も終了コード 0 で通る（2026-09-12 に実測）。
    したがって課題 1〜11 の README に鍵の作成手順は書いていない。
    鍵が要るのは封緘物が初めて出る課題 12 からで、その手順は課題 12 の担当が持つ。
