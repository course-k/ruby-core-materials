# rb1-12-mini-integration-1 — ミニ統合① 得点の集計スクリプト

## この課題の位置と到達点

- 位置: Ruby 軸 / 基礎 / 課題 12（基礎は全 21 課題）。前は `rb1-11-exceptions`、次は `rb1-13-modules-mixins`。
- 到達点: この課題を終えると、次ができるようになる。
  - 課題 1〜11 で 1 つずつ触った道具を**束ねて 1 本の動くスクリプト**にできる。
  - 標準入力・引数・標準出力・標準エラー・終了コードを決められたとおりに扱える。
  - 中身を読めないテストで判定される状況で、要件の文面だけを頼りに実装を詰められる。
- これまでの課題と違い、**何をどう書くかは指示されない**。要件だけが渡され、
  クラスの分け方・メソッドの切り方・例外の使いどころは自分で決める。

## 初めて使う道具

この課題で初めて使うものが 1 つある。

- **`bin/check --start`（封緘物の開封）** — この計画には、**あらかじめ暗号化しておいて、
  決められた時点まで中身を読めなくしてあるファイル**がある。これを「封緘物」と呼ぶ。
  狙いは、解く前に正解や判定条件を見てしまわないようにすることで、
  「答えから逆算して書く」ことを防いで実力を測れるようにするため。開く時点は 3 通りある。
  - **着手したとき**開くもの — この課題の**要件**がこれ。`bin/check --start <課題番号> <成果リポ>`
    を実行すると復号され、置かれた場所のパスが表示される。
  - **判定のときだけ走り、最後まで読めない**もの — この課題の**判定テスト**がこれ。
    `bin/check` が中で復号して走らせ、終わったら消す。落ちたときに見えるのは
    「テスト名」と「失敗メッセージの 1 行目」だけ。
  - **完了後に開く**もの — この課題には無い（課題 20 で出てくる）。

  開封したという事実は `<成果リポ>/.check/<課題番号>.yml` に記録される。
  このファイルは `bin/check` が書くもので、自分で編集しない。

## 前提

- 課題 1 で作った成果リポに `Gemfile` / `.ruby-version` があり、`bundle install` が済んでいること。
- 教材リポ（このファイルがあるリポジトリ）で `bundle install` が済んでいること。
- 課題 2〜11 をすべて終えていること。この課題はその範囲の道具だけで解ける。
- 封緘の鍵が `~/.config/ruby-learning/seal.key` にあること（確かめ方は課題 1 の README の手順 3）。
  無いと `bin/check` は終了コード 2 で止まる。

以降、`<成果リポ>` は自分の成果リポジトリのパス、`<教材リポ>` はこのファイルがあるリポジトリのパスを指す。

## 手順

1. 着手して要件を開く。

   ```sh
   cd <教材リポ>
   bin/check --start rb1-12-mini-integration-1 <成果リポ>
   ```

   復号された要件のパスが表示される（`<教材リポ>/unsealed/rb1-12-mini-integration-1/requirements.md`）。
   これを読む。**この課題の判定条件はこの 1 ファイルが正**で、README は手順だけを持つ。

2. 雛形を置く。

   ```sh
   cd <成果リポ>
   mkdir -p rb1-12-mini-integration-1
   cp <教材リポ>/tasks/rb1-12-mini-integration-1/template/tally.rb rb1-12-mini-integration-1/tally.rb
   ```

   雛形の中身は 1 行だけ（`# frozen_string_literal: true`）。メソッド名も骨組みも入っていないのは、
   そこを決めることがこの課題の中身だから。

3. 実装する。判定は `<成果リポ>/rb1-12-mini-integration-1/tally.rb` を
   `ruby tally.rb ...` の形で別プロセスとして起動する。要件の「入出力」の節が契約。

   手元で動かすには、**開封した要件の「例」の節にある入力**をそのままファイルに書き、
   リダイレクトで流し込む（課題 5 で使った形）。

   ```sh
   cd <成果リポ>/rb1-12-mini-integration-1
   ruby tally.rb < input.txt
   echo $?
   ```

   `input.txt` は自分の確認用なので、中身も名前も置き場所も自由。判定には使われない。

4. 書式を整える。RuboCop はこの課題の判定に含まれない（設計上、実装そのものに集中させるため）。
   自分で掛けて直す。

   ```sh
   cd <教材リポ>
   bundle exec rubocop --config .rubocop.yml <成果リポ>/rb1-12-mini-integration-1/tally.rb
   ```

5. 判定する。

   ```sh
   cd <教材リポ>
   bin/check rb1-12-mini-integration-1 <成果リポ>
   ```

   落ちたときに見えるのはテスト名と失敗メッセージの 1 行目だけ。テスト名は要件に出てくる語だけで
   できているので、要件のどの条項が通っていないかはテスト名から辿れる。

## 完了の判定

`bin/check rb1-12-mini-integration-1 <成果リポ>` が「合格」になり、終了コードが 0 になること
（`echo $?` で見る）。判定条件の正本は開封した `requirements.md` の「完了条件」の節。

## 進捗の記録

記録先は成果リポの `progress.md`。ただし**課題ごとの表は手で書かない**——
`bin/check` が `.check/` から状態と日付を書き直している。手で足しても次に
`bin/check` を走らせたときに消える。開いて自分の行が入っていることだけ確かめる。

振り返りは `rb1-12-mini-integration-1/notes.md` に書く（新規に作る）。表の「なぜこう書くか」欄が
このファイルへのリンクになる。書く内容:

- 要件のどの条項でいちばん手が止まったか。
- 判定が落ちたとき、テスト名から要件のどこを見直したか。

`progress.md` に自分で書くのは、週あたりの目標・未消化にした課題・想起セッションの記録の
3 つだけ。書いたらコミットする。

書いたらコミットする。

```sh
cd <成果リポ>
git add .
git commit -m "rb1-12: 得点の集計スクリプトを実装した"
```
