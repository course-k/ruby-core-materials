# 課題担当 B（rb1-12〜rb1-21）が置いた仮定

最終更新: 2026-09-12

根幹文書 `01-core-spec.md`・設計文書 `10-design-ruby-basic.md`・基盤の手引き
（`docs/materials-guide.md` / `docs/check-yml.md`）に規定が無く、実装者が決めた事柄を列挙する。
後で根幹または設計へ書き写すか、破棄するかを判定するための一覧。

## 置き場とファイル名

1. **課題 16 のディレクトリ名を `complete/` と `debug/` にした。**
   `docs/materials-guide.md` §1 の一覧には中間帯の置き場が無い（`exercise/` と `predict/` だけ）。
   完成問題とデバッグ課題は判定の種別も封緘の有無も違うので、`exercise/` に同居させず分けた。
   成果リポ側も同じ名前（`<成果リポ>/rb1-16-band/complete/lib/` など）。
2. **ミニ統合・ゼロ実装の雛形を `template/` に置いた。**
   根幹 §3.2 は「雛形は判定が読む 1 ファイル、中身は `# frozen_string_literal: true` のみ」とだけ書き、
   教材リポ側の置き場を決めていない。`docs/materials-guide.md` §1 の `template/lib/`・`template/test/` に
   ならい、課題 12 は `template/tally.rb`、課題 20 は `template/lib/*.rb`、
   課題 21 は `template/lib/records.rb` と `template/exe/dedup` にした。
3. **雛形とライブラリのファイル名**（課題 12 `tally.rb`、課題 20 `normalizer.rb` / `ledger.rb` /
   `log_reader.rb`、課題 21 `lib/records.rb` と `exe/dedup`）。設計は題材だけを決めている。
4. **確認課題の題材・クラス名・メソッド名**（課題 13 `VersionTag`、14 `LogLines`、15 `EventRouter`、
   17 `TextStore`、18 `Report`、19 `Counter` と `exe/count`）。設計 §3 は課題 13・14 の題材の方向だけを
   決めており、15・17・18・19 は確認課題の題材を決めていない。

## 判定の作り方

5. **出力予測（課題 16）に封緘物を作らなかった。**
   設計 §5 は「完成問題と出力予測の判定テストは判定時のみ実行」と書くが、`predict` judge は
   判定テストのファイルを持たず、対象コード（学習者が読む）と学習者の予測を比べる仕組みで、
   不一致のときも正解の出力を表示しない（`docs/check-yml.md`）。この judge 自体が
   「判定時のみ」を満たすとみなし、封緘物を作らなかった。
6. **ミニ統合の判定テストが、起動するスクリプトの場所を `$LOAD_PATH` から探す。**
   封緘テストは一時ディレクトリへ復号して実行されるので `__dir__` が使えない。
   `check.yml` の `load_paths` に成果リポ側のディレクトリを並べ、テストの中で
   `$LOAD_PATH` の各要素に目的のファイルがあるかを探す形にした。
   課題 12 は `load_paths: ["."]`、課題 21 は `["lib", "exe"]`。
7. **別プロセスの起動に `RbConfig.ruby`（課題 12）と実行ファイルの直接起動（課題 19・21）を使い分けた。**
   課題 12 のスクリプトは実行権限を学習内容にしていないので `ruby <path>` の形で起動する。
   課題 19・21 は実行権限と shebang が学習内容なので、パスをそのまま起動して権限の有無まで見る。
8. **課題 21 で「処理の本体を `exe/` に書かない」ことを判定に載せた。**
   `exe/dedup` の中身を読んで `Data.define` や `class *Entry` が無いこと、`require_relative` が
   あることを確かめている。設計 §3 は「exe/ と lib/ を分け」としか書いていないので、
   分離を機械で見る線をここに引いた。
9. **課題 21 の「学習者が自分のテストも書く」を機械判定に載せなかった。**
   根幹 §4.2 の「判定を持たない工程も完了条件に数える」に従い、要件と README の完了条件に
   文章で置いた。基盤の仮定 3（自分で足した assert は判定対象にしない）とも揃う。
10. **使い方エラーの終了コードと文言**（課題 12 `usage: tally [min-score]`、
    課題 21 `usage: dedup [options] FILE`、どちらも終了コード 2）。
    設計は「入出力契約（…終了コード…）まで確定する」とだけ書き、値を決めていない。
    `bin/check` の終了コード（0 合格 / 1 失敗 / 2 使い方エラー）と同じ割り当てにした。
11. **課題 12 の使用禁止に `require` / `require_relative` を足した。**
    設計 §3 は「使用禁止は課題 13 以降の行の機能」で、表から導くと B9〜B14。
    標準ライブラリの読み込み自体は名指しされていないが、B12〜B14 が読み込みを伴う以上
    禁止側に寄せた（この課題は読み込み無しで解ける）。
12. **課題 14 の確認課題で、値オブジェクトのどの項目を等価性に含めるかを問わない形にした。**
    設計 §3.1 は課題 14 に「等価性の定義（何をもって同じ行とみなすか）」を学習者の判断として残している。
    判定テストは「同じ文字列から作った 2 つが等しい」「本文が違えば別」だけを見て、
    時刻を項目に含めるかどうかは問わない。

## 文書の書き方

13. **原本の冒頭に底本 URL のコメント段落を置き、「写さなくてよい」と README に書いた。**
    根幹 §3.1 は「識別子ごとに実在する節の URL を付す」と規定するが、写しの対象に含めるかは
    決めていない。アサーション数と書式だけを見る判定なので、写さなくても合格する。
14. **課題 16 に `why.md` と `commentary.md` を置かなかった。**
    設計 §5 の judge 表は中間帯にテストしか挙げていない。書き写しではないので
    「なぜこう書くか」欄を求めず、その旨を README に理由付きで書いた（根幹 §4.2 の同形式間の整合）。
15. **「封緘」の学習者向けの定義を課題 12 の README に置き、以降の課題（16・20・21）はそこを指す。**
    設計 §3.2 は課題 12 で「学習者向けに『封緘』を定義する」とだけ書いている。
    3 値（着手後 / 判定時のみ / 完了後）をまとめて定義し、課題 20 の README では
    「完了後に開くものが初めて出てくる」とだけ書いた。
16. **課題 20 の judge 名を「ゼロ実装 01 / 02 / 03」にし、クラス名を出さなかった。**
    judge 名は `bin/check` を打てば着手前でも見えるため。
17. **JS 対比の底本で、MDN に対応ページが無い領域は Node.js / npm の公式ドキュメントを第 2 の底本にした。**
    根幹 §3.1 は「JS 側は MDN を底本にする」と書くが、ファイルシステム（課題 17）と
    実行ファイルの登録（課題 19）は MDN の範囲外。MDN で書ける部分（`try...finally`）は MDN を引き、
    それ以外は `nodejs.org` / `docs.npmjs.com` を引いて、`commentary.md` の底本一覧に両方を並べた。
18. **各課題の README の節構成をそろえた**（位置と到達点 / 初めて使う道具 / 前提 / 手順 /
    完了の判定 / 進捗の記録 / 次の課題）。根幹 §4.2 は要素を列挙するが、順序と見出し名は決めていない。
19. **書き写し課題で、学習者が自分の assert を書く先を
    `<成果リポ>/<課題番号>/exercise/test/<name>_test.rb` に決めた**（判定には含まれない）。
    基盤の仮定 3 が「学習者側のテストファイル」に書くとしているが、パスを決めていない。
20. **課題 18 と 19 の README に「他の書き写し課題との差について」の節を置いた。**
    根幹 §4.2 の「同形式間の整合」が求める「差の理由を学習者に向けて書く」への対応。
