# `check.yml` のスキーマ

最終更新: 2026-09-12

`tasks/<課題番号>/check.yml` は、その課題で `bin/check` が何を見るかを書いたファイル。
設計文書「Ruby 基礎」§5 の「形式別 judge 表」をファイルへ写したものにあたる。
実例は `tasks/rb1-00-selfcheck/check.yml`（judge 8 種すべてを使う検体）。

パスの基準はふたつある。取り違えると judge が黙って「未着手」になるので、各 judge の表で明示する。

- **教材リポ側**: `tasks/<課題番号>/` からの相対パス
- **成果リポ側**: `<成果リポ>/<submission_dir>/` からの相対パス

## トップレベル

| キー | 必須 | 値 |
|---|---|---|
| `task` | 任意 | 課題番号。書いた場合はディレクトリ名と一致していないと使い方エラー（終了コード 2） |
| `title` | 任意 | 判定出力の見出しに出る課題名 |
| `format` | 任意 | 課題形式の覚え書き（`bin/check` は読むだけで使わない）。設計文書の形式名を書く |
| `submission_dir` | 任意 | 成果リポ内の課題ディレクトリ名。既定は課題番号（根幹 §6 の配置契約どおり） |
| `judges` | 必須 | judge の配列。書いた順に実行し、書いた順に表示する |
| `sealed` | 任意 | 封緘物と開封タイミングの配列 |

## `judges` の共通キー

| キー | 必須 | 値 |
|---|---|---|
| `type` | 必須 | judge の種別（下表） |
| `id` | 任意 | `--report` のログに出る識別子。既定は `type` |
| `name` | 任意 | 判定出力に出る表示名。既定は `type`。学習者が読むので日本語で書く |

judge は `合格` / `失敗` / `未着手` のいずれかを返す。**判定の対象がまだ存在しないときは「失敗」ではなく
「未着手」**（根幹 §6）。1 つでも `失敗` があれば終了コード 1、無ければ 0。すべてが `合格` のときだけ
`.check/<課題番号>.yml` の `status` が `passed` になり、`on_complete` の封緘物が開く。

## judge の種別

### `copy_run` — 写しの実行（失敗ゼロ）

書き写し課題のうち課題 3（手本がテストファイル）と検体 rb1-00 だけが使う。他の書き写し課題の写しは
`exercise_test` の照合テストが読み込むので、この judge を並べない。

| キー | 基準 | 説明 |
|---|---|---|
| `submission` | 成果リポ側 | 学習者が書き写した `.rb`（minitest のテストクラス） |

成果リポの Gemfile で実行する。`<課題ディレクトリ>/lib` と `<課題ディレクトリ>/test` があれば
`-I` に足す。ファイルが無ければ「未着手」。

### `assertion_count` — アサーション数 ≧ 原本、テストメソッド数 ≧ 原本

書き写し課題のうち課題 3（手本がテストファイル）と検体 rb1-00 だけが使う。

| キー | 基準 | 説明 |
|---|---|---|
| `submission` | 成果リポ側 | `copy_run` と同じファイルを指す |
| `min` | — | 原本のアサーション数（整数）。**原本を実際に走らせて実測した値**を書く |
| `runs_min` | — | 任意。原本のテストメソッド数（実行サマリの `N runs`。整数）。**実測値**を書く。省略または 0 のときはテストメソッド数を見ない |

数は minitest の実行サマリ `N runs, M assertions` から読む（`assert` 行を静的に数えない、根幹 §6）。
`min` / `runs_min` の測り方: `bundle exec ruby tasks/<課題番号>/original/<name>_test.rb` の最終行
（`N runs, M assertions, ...`）を読み、`N` を `runs_min`、`M` を `min` に書く。

`runs_min` を置く理由: `min` だけだと、1 つのテストメソッドに `N.times { assert true }` と書いた
中身の無い写しが通ってしまう。テストメソッドの本数は原本の構造をなぞらないと満たせない。
両方を満たさないときは、足りない側（または両方）を 1 行ずつ表示して失敗にする。

### `rubocop` — 書式（根幹 §3.1 の cop 構成）

| キー | 基準 | 説明 |
|---|---|---|
| `submission_paths` | 成果リポ側 | 検査するファイルの配列 |

教材リポの Gemfile と教材リポの `.rubocop.yml` で実行する（根幹 §6）。指摘が出た行をそのまま表示する。

### `why_diff` — `why.md` が雛形と差分あり

| キー | 基準 | 説明 |
|---|---|---|
| `template` | 教材リポ側 | 雛形。既定 `why.md` |
| `submission` | 成果リポ側 | 学習者の記述。既定 `why.md` |

前後の空白を落として比較し、**一致していたら失敗**（雛形のコピーでは通らない）。中身の合否は判定しない。

### `exercise_test` — 確認課題テスト・写しの照合

| キー | 基準 | 説明 |
|---|---|---|
| `test` | 教材リポ側 | 判定テストの**正本**。学習者が読んでよい（確認課題のテストは封緘しない、根幹 §3.1） |
| `load_paths` | 成果リポ側 | `-I` に渡すディレクトリの配列 |
| `requires` | 成果リポ側 | 任意。ここに挙げたファイルが無ければ「未着手」にする |

正本を一時ディレクトリへ複写して実行し、残さない（根幹 §6）。学習者が自分で足す assert は学習者側の
テストファイルに書き、この judge は見ない（§3.1 の「自分で足す assert」は判定対象ではない）。

書き写し課題（課題 3 を除く）では、同じ judge を**写しの照合**にも使う。`test` に教材側の
`copy_test/<name>_test.rb`、`load_paths` に写しの置き場 `.`、`requires` に写しのファイル名 `<name>.rb` を書く。
照合テストは写し（定義だけ）を `require` し、定義したメソッド・クラスを自分で呼び出して戻り値・出力・例外を
照合する。写しの構文エラーは読み込みで、定義の欠落は `NameError` / `NoMethodError` で失敗になる。写しが無いときの未着手表示は確認課題と同じ文言
（「確認課題がまだありません: <写しのパス>」）で出る——別の種別は設けていない（`copy_check` は無い）。

### `sealed_test` — 封緘テスト（判定時のみ実行）

| キー | 基準 | 説明 |
|---|---|---|
| `sealed` | — | `sealed:` に登録した**平文のファイル名**（`sealed/<名前>.enc` の `<名前>`） |
| `load_paths` | 成果リポ側 | `-I` に渡すディレクトリの配列 |
| `requires` | 成果リポ側 | 任意。ここに挙げたファイルが無ければ「未着手」にする |

指す封緘物の `open` は `judge_only` でなければならない（違えば失敗として報告する）。復号先は一時
ディレクトリで、実行後に消える。失敗時の表示は「テスト名＋失敗メッセージ 1 行目」に限られる。

### `predict` — 出力予測

| キー | 基準 | 説明 |
|---|---|---|
| `source` | 教材リポ側 | 出力を予測させる対象コード（`predict/NN.rb`） |
| `expected` | 成果リポ側 | 学習者が書き下した予測（`predict/NN.txt`） |

対象コードを教材リポの Gemfile で実行し、標準出力と完全一致するかを見る（末尾の改行だけ無視する）。
不一致のときは最初に食い違う行番号だけを返し、正解の出力は表示しない。

### `template_test` — 雛形テストの実行

| キー | 基準 | 説明 |
|---|---|---|
| `test` | 成果リポ側 | 学習者が置いた雛形テスト |
| `load_paths` | 成果リポ側 | `-I` に渡すディレクトリの配列 |

教材が与えた雛形を成果リポで動かせているかを見る judge（設計文書 §5 の課題 1「雛形テストの実行」）。
`exercise_test` と違い、テストは成果リポ側にある。

## `sealed`

```yaml
sealed:
  - file: requirements.md            # 平文のファイル名。実体は sealed/requirements.md.enc
    open: on_start                   # 開封タイミング（3 値）
```

| `open` | 意味 | いつ開くか |
|---|---|---|
| `on_start` | 着手後 | `bin/check --start` が `unsealed/<課題番号>/` へ復号してパスを表示する |
| `judge_only` | 判定時のみ実行 | `sealed_test` が一時ディレクトリへ復号して実行し、消す。学習者は中身を読めない |
| `on_complete` | 完了後 | 全 judge が合格した回の `bin/check` が `unsealed/<課題番号>/` へ復号する |

3 値以外を書くと使い方エラー（終了コード 2）。封緘物の作り方は `docs/materials-guide.md`。

## 形式別のひな型（設計文書「Ruby 基礎」§5 の judge 表に対応）

| 形式 | 並べる judge |
|---|---|
| 書き写し | `exercise_test`（写しの照合、`copy_test/`）/ `rubocop` / `why_diff` / `exercise_test`（確認課題。課題 7 は `predict`、課題 9 は両方）。課題 3 のみ `copy_run` / `assertion_count` / `rubocop` / `why_diff` / `exercise_test` |
| ミニ統合〈道具の 1 周〉（課題 1） | `template_test` / `rubocop` |
| 中間帯・完成問題とデバッグ | `exercise_test`（または `sealed_test`） |
| 中間帯・出力予測 | `predict` |
| ゼロ実装（課題 20） | `sealed_test` |
| ミニ統合（課題 12・21） | `sealed_test` |

設計文書 §5 は課題 1 の judge に「`.check/` の存在」を挙げているが、`.check/<課題番号>.yml` は
`bin/check` 自身が毎回書くので、judge にはしていない（`docs/materials-guide.md`「基盤担当が置いた仮定」）。
「RuboCop は表示のみで合否に含めない」形式（課題 12・20・21）では、`rubocop` judge を並べずに
学習者が自分で `bundle exec rubocop` を掛ける手順を課題文書に書く。
